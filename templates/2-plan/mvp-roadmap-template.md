# Stage 2 — 产品计划 / MVP & Roadmap

> 把 Stage 1 的概念拆成**有取舍的、可执行的**三层路线图：MVP / V1 / V2+。
> 我会在这里**逼你砍**——B 端产品 MVP 的最大杀手就是"什么都想要"。

## 拆分原则

### 三层

| 层 | 时间窗 | 内容 | 必须成立的判定 |
|---|---|---|---|
| **MVP** | 前 4-8 周 | 单一最痛 workflow，端到端跑通 | 用户单独用就有价值，没有 V1 也能交付 |
| **V1** | MVP 后 4-12 周 | 围绕 MVP 的护城河 + 关键 retention 功能 | 有它产品才能 *持续* 被用，没它用户用 1 次就走 |
| **V2+** | 12 周以后 | 平台化 / 集成 / 高级特性 | 没它不影响产品**第一次**成功 |

### MoSCoW 过滤器

每个 feature 走一遍：

- **M**ust have — 没了 MVP 不成立
- **S**hould have — 强烈想要但 MVP 不放也行
- **C**ould have — 锦上添花
- **W**on't have (this time) — 主动决定不做

**判定标准**：MVP 的 Must 列表 ≤ 8 项。如果你列出 15 个 Must，**有问题**——回去重审 Stage 1 的"价值主张"，看是不是你想做的太多。

### "Single most-painful path" 过滤器

最关键的问题：

> 如果产品只做一件事 / 只跑一条 workflow，哪条 workflow 必须 work？

举例（沿用 Stage 1 的客户提案管理例子）：

- ❌ 错误的 MVP path：搜索 + 多版本管理 + 评论 + 权限 + 集成 Figma + AI 摘要
- ✅ 对的 MVP path："上传一份提案 → 标记为某客户 → 客户回复后能看到当前批了哪版"

砍掉所有不服务于这条 path 的 feature，哪怕它们看起来都很合理。

## 模板

### Feature dump (无序 / 不取舍)

先把**所有想到的**写下来，别管优先级：

```
- 提案上传
- 提案版本管理
- 客户审批
- 客户评论
- @mention
- Slack 通知
- 评论 thread
- AI 摘要提案重点
- 数据看板（看了多少次）
- 集成 Figma
- 模板库
- 权限管理（谁能看谁不能看）
- 提案 PDF 导出
- 多语言
- ...
```

### MoSCoW + 价值-成本 矩阵

```
┌─────────────────┬─────────┬────────┬───────────┐
│ Feature          │ MoSCoW  │ 价值    │ 成本     │
├─────────────────┼─────────┼────────┼───────────┤
│ 提案上传         │ M       │ 高     │ 低 (1d)   │
│ 提案版本管理     │ M       │ 高     │ 中 (3-5d) │
│ 客户审批         │ M       │ 高     │ 中 (3d)   │
│ Slack 通知       │ S       │ 中     │ 低 (1d)   │
│ 集成 Figma       │ C       │ 中     │ 高 (10d)  │
│ AI 摘要          │ C       │ 中     │ 中 (3d)   │
│ 多语言           │ W       │ 低     │ 高        │
└─────────────────┴─────────┴────────┴───────────┘
```

### 输出三层 Roadmap

```markdown
# <产品名> — Roadmap (v0.1)

## MVP (前 6 周)
**目标**：跑通 single most-painful path = 上传提案 → 关联客户 → 客户审批 → 显示当前版本。

| Feature | 为什么 MVP 必须有 | 估算 |
|---|---|---|
| 提案上传 | 没法开始 | 1d |
| 客户关联 | 区分多客户 | 1d |
| 版本管理 | 区分批了哪版 | 3d |
| 客户登录审批 | 确认权属 + 审批 | 3d |
| 当前版本显示 | 解决核心痛 | 2d |
| ... 4 项以内 | | |

**总估算**：~4 周开发 + 2 周内测 = 6 周可交付

## V1 (MVP 后 6 周)
**目标**：让 MVP 产生 retention，避免用户用一次就走。

| Feature | 为什么 V1 |
|---|---|
| 评论 / @mention | 让 PM-客户对话留在产品内 |
| 提案模板库 | 提高新建提案速度，复购的关键 |
| Slack 通知 | 客户审批后 PM 第一时间知道 |
| ... |

## V2+ (3 个月以后)
| Feature | 为什么 V2+ |
|---|---|
| 集成 Figma | 锦上添花的连接 |
| AI 摘要 | 高价值但非核心 |
| 数据看板 | 等有数据再做 |
| 多语言 | 等海外有客户再做 |

## 主动决定不做
- ❌ 多公司团队权限 (我们做单团队产品)
- ❌ 提案模板编辑器 (用 Figma 编辑，导入即可)
- ❌ 复杂审批流 (单人审批就够)
```

## 反 anti-pattern 检测

我会拒绝这几类计划：

- ❌ **MVP 包含集成**（"集成 X" 永远是 V1+）
- ❌ **MVP 包含 AI 智能 X**（先把非 AI 的 X 跑通再叠 AI）
- ❌ **MVP 包含 admin 后台**（除非 admin 就是用户）
- ❌ **MVP 包含权限矩阵**（先做单角色，权限 V1+）
- ❌ **MVP 时间 > 12 周**（太长，团队会失焦，做完 60% 就被业务推翻）

## 完成 Stage 2 之后

你拿到一份 `roadmap.md`，可以：
- 给同事 / 投资人 / 老板看，确认范围
- 估算 MVP 实际人月，决定要不要拆
- 进入 Stage 3 (Feature)，把 MVP tier 的每个 feature 写成可实施的 spec
